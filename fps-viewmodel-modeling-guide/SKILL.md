# FPS Viewmodel Modeling Guide

## Overview

本 Skill 让 AI 具备对 FPS 游戏 viewmodel（第一人称视角专用模型）正确建模方式的理解，能够在
用户讨论建模方案、骨骼绑定、动画流程或引擎导入时，给出符合主流 FPS 游戏工程实践的建议，而非
泛泛的"建模原则"。所有判断均以本节"核心知识框架"的八条规范为依据。

## 触发条件

当用户输入出现以下任一信号时激活本 Skill：

- 关键词："viewmodel 建模""第一人称武器模型""FPS 持枪模型""FPS 持刀模型"
  "第一人称手臂绑定""第一人称手臂""viewmodel 动画""持刀模型""持枪模型"
- 讨论内容涉及：viewmodel 双模型架构、武器与手臂的父子层级、viewmodel 的 FOV/原点设置、
  第一人称手臂骨骼命名与层级、draw/holster/idle/reload 等 viewmodel 动画状态规划、
  从 Blender/Maya/3ds Max 向 Source/Unreal/Unity 导入 viewmodel 后的比例失调或位置异常。
- 用户贴出 viewmodel 截图、工程文件，或询问"这个比例对不对""模型怎么跑到屏幕中间了"
  "换弹时手穿墙了"等典型 viewmodel 问题。

## 强制响应流程（每次回复前先执行）

1. **先确认环境，再给建议。** 在给出任何针对性建议前，先确认两项：
   - 目标引擎（Source / Source 2 / Unreal / Unity / 自研，或其他）；
   - 建模软件（Blender / Maya / 3ds Max / ZBrush + 拓扑软件）。
   若用户未说明，主动询问，不要基于假设直接下结论。
2. **比例/位置类问题必须先反查 FOV。** 当用户问"这个模型比例对不对""模型是不是太大了"
   时，**先反问用户：当前建模用的 FOV 设的是多少？** 在拿到 FOV 前，不轻易判断比例正误
   （见第三、八条）。
3. **默认采用双模型架构与摄像机子物体层级**，不要提议用单一全模型替代（见第二、五条）。
4. **发现潜在陷阱时主动指出**，不要等用户提问（见第八条清单）。
5. **语气保持技术指导口吻**：给出具体数值、架构决策与可操作步骤，避免空泛原则。

## 核心知识框架

### 一、viewmodel 的本质定位

Viewmodel 是独立于玩家身体模型（worldmodel）的专用模型，只对本地玩家渲染，仅从有限视角被
观看 [ref:0]。它与普通游戏模型的设计原则不同：

- 玩家看不到的部分应直接删除（背面、内侧、被遮挡的几何）。
- 玩家能看到的部分需要高细节。
- 整体为单一观看角度优化，不是为 360° 审视设计。

因此，讨论 viewmodel 建模时**默认这一前提**，不要建议把 viewmodel 做成完整的、可 360°
审视的模型。模型"完整性"在这里是减分项而非加分项。

### 二、双模型架构（必须理解并默认采用）

主流 FPS 游戏采用两套独立模型 [ref:1]：

- **完整玩家模型**（worldmodel）：存在于游戏世界中，供其他玩家看见、产生阴影、受击判定；
  对本地玩家自身设为不可见。
- **Viewmodel**：渲染在摄像机的独立图层中，不参与物理碰撞。

武器和手臂通常是摄像机下的子物体，但**不跟随摄像机的物理惯性旋转，只跟随瞄准方向** [ref:2]。
给出建议时默认此架构；不要提议用单一全模型方案替代双模型方案。

### 三、FOV 与原点对齐（硬性规范）

1. **在正确的 FOV 下建模。** Source 引擎默认使用 54° FOV 来近似人眼视角，而非世界视图的
   75°，这样模型才能以正确比例呈现 [ref:3]。其他引擎（Unreal/Unity）需使用项目约定的
   viewmodel FOV（常见 60–90° 区间，但必须与该引擎的实际第一人称 FOV 一致），不可套用世界
   场景的第三人称 FOV。
2. **原点必须在 0,0,0 世界中心。** 所有物体（含骨骼）的原点放置在 0,0,0，原点即游戏中摄像机
   的位置 [ref:4]。
3. **边看边调。** 建模时必须保持一个匹配该 FOV 与原点设置的摄像机可见，在正确取景下调整比例
   与位置 [ref:5]。在建模软件中看不到摄像机就盲调位置，是第八条第 5 款的经典错误。

讨论比例、位置调整时，**先确认 FOV 设置是否正确**，再判断其他问题。

### 四、骨骼层级与绑定原则

第一人称手臂需要绑定到一套模拟人臂自然运动的骨骼层级上 [ref:6]：

- 层级根部（root bone）位于世界中心，**无旋转** [ref:7]。
- 手臂骨架通常包含：root、上臂/前臂骨骼、手腕 twist helper（改善变形）、以及武器
  attachment 骨骼。
- 武器本身也是蒙皮几何体，有自己的骨骼层级和 attachment helper [ref:8]。
- 在 Source 引擎中，骨骼命名必须与原版骨架层级一致，否则会影响阴影投射等行为 [ref:9]。

原则：保持层级简洁，**不要添加玩家永远看不到的骨骼**（如完整脊柱、腿部、脚趾等中继骨骼）。

### 五、武器与手臂的父子关系

- 武器模型作为**手臂的子节点**，手臂作为**摄像机的子节点** [ref:10]。
- 这样换弹、后坐力等动画可独立于身体骨骼驱动，手永远不会穿模进墙体 [ref:11]。

讨论"武器怎么跟手配合"时，**默认武器挂在手臂骨骼下**，而不是让手臂 IK 去追武器——后者是
full-body（全身）方案的做法，不适用于标准 viewmodel。

### 六、动画状态的最低要求

Viewmodel 至少需要绑定 idle 动画才能正常显示 [ref:12]。必须覆盖的基础动画状态：

- `draw`（拔出）、`holster`（收起）、`idle`（待机）、`fidget`（检视）
- `primaryattack`（开火）、`reload`（换弹）、`dryfire`（空仓扣扳机）

近战武器还需 `hitleft` / `hitright` 等攻击动画 [ref:13]。

讨论动画规划时提醒用户：**不要只做 idle 和开火就交付**，需覆盖上面这一整套状态机。

### 七、近战武器（持刀）与枪械的区别

近战武器 viewmodel 与枪械共享第一至第六条全部架构原则，但动画侧重点不同 [ref:14]：

- **枪械**重点：后坐力、换弹、开镜（ADS）。
- **近战**重点：挥砍/刺击的轨迹、与准星的可视关系（刀刃不能遮挡准星太久）、收刀/出刀的过渡
  动画。

关键区分：近战武器的**"攻击判定范围"**与**"动画表现范围"**需分开考虑——判定范围由代码/碰撞
体决定，动画表现范围只负责观感，两者解耦。讨论持刀 viewmodel 时主动点明这两类武器动画优先级
的差异。

### 八、常见陷阱（对话中主动预警）

用户在建模 viewmodel 时最易犯的错误，发现苗头即主动指出 [ref:15]：

1. 在**错误的 FOV** 下建模 → 引擎内比例失调。
2. **原点不在 0,0,0** → 模型出现在屏幕中央而非手中。
3. 骨骼层级中添加**不必要的中继骨骼** → 增加复杂度、拖累权重。
4. 武器与手臂**未建立正确父子关系** → 动画不同步。
5. 建模软件中**看不到摄像机就盲调位置** → 取景错误。

当用户描述的症状命中以上任一条时（如"换弹时手穿墙了""模型在屏幕正中间""导入后枪好大"），
直接点出对应陷阱并给出纠正步骤，不要只回答表面问题。

## 决策检查表（应用本 Skill 时逐项核对）

- [ ] 是否已确认引擎与建模软件？（未确认先问）
- [ ] 比例/位置问题是否先反查 FOV？（未查 FOV 不判比例）
- [ ] 是否默认双模型架构、viewmodel 在摄像机独立图层？

- [ ] 动画状态是否覆盖 draw/holster/idle/fidget/primaryattack/reload/dryfire（近战另加 hit）？
- [ ] 是否识别并预警了第八条中的常见陷阱？
